# 模型权重

本目录存放推理用的模型权重。**权重不进版本库**（见根目录 `.gitignore` 的
`models/*.pt`）—— 仅 `jktk_x.pt` 就有 436MB，远超 GitHub 单文件上限。

## jktk_x.pt（当前使用）

| 项 | 值 |
|---|---|
| 架构 | YOLO**11**x |
| 类别数 | 116 |
| 体积 | 436 MB |
| 许可证 | apache-2.0 |
| 来源 | `hf-mirror.com/hodoly163/krishibondhu-jktk` |

### 获取方式

从上述仓库下载 `jktk_x.pt`，放到本目录即可。后端通过
`server/app/config.py` 的 `DEFAULT_WEIGHTS` 定位它；**换权重 = 改这一行**，
API 契约与前端一行不动。

### ⚠️ 这个权重只用来「判型」，不用它「定位」

实测结论（详见 `server/app/services/lesion.py` 的模块 docstring）：

- **判型准** —— 真实照片上 纹枯病 0.947 / 稻瘟病 0.965
- **定位假** —— 它输出的框是 `(0.001, 0.033, 0.997, 0.934)`，**盖住整图约 93%**

原因：这个权重是**图像分类数据集被导出成检测格式**训练的 —— 所谓"框"就是整图。
模型学会了"这张图是什么病"，从未学过"病斑在哪"。116 类里也**没有任何水稻害虫类**，
且存在合并数据集的重复标签。

因此系统的分层架构是：

```
上传图片
  ├─ 第一步  YOLO(jktk_x.pt)      ──► 只取 top-1 类别与置信度，**丢弃它的框**
  └─ 第二步  病灶定位
       ├─ 2a 类无关分割(FastSAM-s) ──► 挑出「泥水」对象
       └─ 2b HSV 图像分割         ──► 减去泥水后，找真实病斑，逐连通域出框
              └─► build_detections() 把第一步的类别贴到第二步的框上
```

API 响应里用 `localization.method`（`"lesion-cv"` 或生效时的 `"lesion-cv+fastsam"`）、
`yoloBoxIgnored = "whole-image"` 把这件事**显式透出**，不让"YOLO 精准定位"变成一句虚话。

### 溯源核查

该权重是从外部镜像拉取的 checkpoint，属于**对外部数据的可执行反序列化**，
落盘前经 `tools/scan_checkpoint.py` 静态反汇编核查：36 个调用目标全部是
`torch.*` / `ultralytics.*`，无 `os` / `subprocess` / `socket` / `ctypes` / `exec`。

### 已知残留限制

当病组织与颜色相近的背景**连成一片**时，会被分割层的面积上限
`AREA_MAX_RATIO = 0.25` 整块拒绝（纹枯病样例右侧另有一片病鞘因此未单独出框）。
这是颜色分割的固有边界 —— 也正是真实系统要换成训练好的分割模型的原因。
答辩时建议主动说明。

**若日后拿到病斑级检测数据集，只需替换第二步**（分割层），第一步与整个 API 契约不变。

## FastSAM-s.pt（定位辅助，可选）

| 项 | 值 |
|---|---|
| 架构 | FastSAM-s（YOLOv8-seg 骨干的类无关分割） |
| 体积 | 23.9 MB |
| 许可证 | **AGPL-3.0** |
| 来源 | 官方 ultralytics 资产，`github.com/ultralytics/assets` 的 `v8.3.0` release |

### 它做什么

**只做一件事**：把画面切成一个个对象，好让 [lesion.py](../server/app/services/lesion.py)
把「泥水」从病灶候选里减掉。它**不判病害类型** —— 类型永远由 `jktk_x.pt` 负责。

为什么需要它：稻田泥水是褐色，落进 HSV 的褐色分支，与植株基部的褐色病斑连成
**一个占图 45.5% 的连通域**，超过 `AREA_MAX_RATIO` 被整块丢弃 —— 真病斑是它的
一部分，跟着一起没了。颜色与几何的启发式修不掉这个问题（实测否决了 5 种），
必须引入"对象"这一层信息。

### 许可说明（如实记录，不美化）

ultralytics **本身就是 AGPL-3.0 依赖**，所以 AGPL 暴露在引入本权重之前就已存在；
换 FastSAM-s 权重不新增**库级**风险。这是一处权衡，不是干净的优势。

### 缺这个文件会怎样

**不是错误。** `Segmenter.load()` 绝不抛异常：文件缺失 / 导入失败 / 预热失败
一律置 `mode="degraded"`，定位自动回落到纯 HSV 路径，输出与引入本权重之前
**逐字节相同**，`localization.method` 也退回 `"lesion-cv"`。日志会记一条 warning。

### 溯源核查

与 `jktk_x.pt` 同类（`.pt` 是 pickle），落盘前经
`tools/scan_checkpoint.py` 静态反汇编核查：**425 个 zip 成员、1 个 pickle
（`FastSAM-s/data.pkl`）、45125 条 opcode、27 个调用目标全部是 `torch.*` /
`ultralytics.*`**，无 `os` / `subprocess` / `socket` / `ctypes` / `exec`，判定 `[通过]`。

### 实测表现（`tools/ab_lesion.py`）

| 图 | 纯 HSV | +FastSAM 减泥水 |
|---|---|---|
| 稻瘟病 599×440 | 9 框 | **9 框，逐字节相同**（未挑出泥水 → 降级） |
| R-C.jfif 640×392 | 29 框 | **29 框，逐字节相同**（未挑出泥水 → 降级） |
| 纹枯病 474×205 | 1 框，框内病斑色 49% | 5 框，首框病斑色 **60%** |
| OIP-C 474×561（稻田泥水） | 9 框，**前三个全是泥水色** | 11 框，出现框内病斑色 **80%** 的真框 |

**已知残留**：OIP-C 那张图上 FastSAM 把**基部褐色病斑与褐色泥水合并成了一个对象**，
减泥水时病斑跟着被减掉（基部 56.9% 的病斑色像素落在泥水掩膜内），
因此基部病灶仍未出框；且首位框是一个 3.55% 的虚焦背景框。
（试过"减泥水时保护其中强病斑色的像素"，实测反而更糟 —— 首位框涨到 13.14%，已否决。）

**调参提示**：`SEG_CONF` 必须压到 **0.15**，这不是随手写的 —— 官方默认 0.4 时
泥水对象**根本不会出现**（置信度天生偏低），整套装置就白装了。详见
[segmenter.py](../server/app/services/segmenter.py) 的常量区。

## 虫害闸门：yolo11s-pest-ip102（**已接线**）

> 曾经的候选 B `insect-detection-yolov8m.pt` 已否决，理由见下。

### 为什么需要

两个已有权重都覆盖不了虫害：`jktk_x.pt` 的 116 类里**没有任何水稻害虫类**；
FastSAM 是类无关分割，不问类别；而 [lesion.py](../server/app/services/lesion.py)
的 HSV 定位找的是**褐/黄/坏死斑** —— 虫子不是斑。所以虫害这张图现在只会得到
「疑似病斑 · 建议取样送检」，类型和位置都给不出来。

判据由 [probe_pest.py](../tools/probe_pest.py) 统一给出，**风险面优先于收益面**：
一个在病害图上乱出虫框的权重会把 `infectedAreaRatio` / `severityLevel` /
`counts` 一起污染，比"认不出虫"严重得多。所以先量三张病害图的出框数。

### 采用者：`yolo11s-pest-ip102.pt` —— 只当「虫/非虫」闸门

| 项 | 值 |
|---|---|
| 架构 | YOLO11**s**（opcode 里出现 `C3k2`/`C2PSA`/`PSABlock`，已确证） |
| 类别数 | 102（IP102） |
| 体积 | 38,317,890 B |
| 许可证 | MIT |
| 来源 | `hf-mirror.com/underdogquality/yolo11s-pest-detection`（`best.pt`） |
| SHA256 | `810f0df179aec54f5d9762a11df4a147ff87ef79ca46649151914eeed260237f` |

溯源核查：`scan_checkpoint.py` `[通过]` —— 764 个 zip 成员、1 个 pickle
（`archive/data.pkl`，178,655 B）、64,631 条 opcode、**39 个调用目标全部是
`torch.*` / `ultralytics.*` / `numpy.*` / `collections` / `_codecs`**。

**实测表现**（`probe_pest.py`，同机 CPU）

| 图 | conf=0.25 | conf=0.5 | 说明 |
|---|---|---|---|
| 稻瘟病 599×440 | **0 框** | **0 框** | 闸门安静 ✅ |
| 纹枯病 474×205 | **0 框** | **0 框** | 闸门安静 ✅ |
| OIP-C 474×561（稻田泥水） | **0 框** | **0 框** | 闸门安静 ✅ |
| 剖茎幼虫照 2791×2091 | 1 框 | 1 框 | `flax budworm` 0.658 |

**结论：闸门质量好，定种不可靠。**

- **可用**：三张病害图两档 conf 全部 0 框 —— 它不会污染现有的病害识别结果。
- **不可用**：唯一的害虫照上它给的是 `flax budworm`（亚麻害虫，**错**），
  框还圈住整段受损茎、不贴虫体；`asiatic rice borer`（二化螟）连 conf=0.02
  都没出现。
- **级联能不能救？不能直接采信**：裁到检出框再跑一次得到
  `asiatic rice borer` 0.519（对），但换四种裁剪得到**四个不同答案**
  （flax budworm / asiatic rice borer / corn borer / rice leaf caterpillar）。
  这说明它"看见了虫"但**定种头不稳** —— 正是"数字看着对"的形态，
  不做能力交付。

### 已否决的候选：`insect-detection-yolov8m.pt`

`hf-mirror.com/Mustafa5645344/insect-detection-yolov8`，MIT，46,801,815 B，
SHA256 `5dd71144e14baf85f3898fecddb4cd6671d9d9c9d73750b59ae805441573a177`，
`scan_checkpoint.py` `[通过]`（24 个调用目标，出现 `C2f` → 确为 YOLOv8）。

**实测表现 —— 两个方向都比 A 差：**

| 图 | conf=0.25 / 0.5 |
|---|---|
| 稻瘟病 599×440 | **5 框**，全部 `planthopper`（**稻飞虱**），最高 conf **0.929** ❌ |
| 纹枯病 474×205 | 0 框 |
| OIP-C 474×561 | 0 框 |
| 剖茎幼虫照 2791×2091 | **0 框** ❌ 真害虫照完全漏检 |

在一张**稻瘟病叶片照**上以 0.929 置信度报出 5 处稻飞虱，这正是上面说的最坏
形态；而真正的害虫照它一框不出。**在病害图上误报、在害虫图上漏检，双向失效。**

附带的可信度问题：它的模型卡只列了 **18 类**，实际模型是 **21 类**
（多出 `green_lacewing` / `rhino_beetle` / `rice_bug`）—— 卡片与权重的类别表
对不上，其自报指标（`stem_borer` mAP@50 0.992）也不应直接采信。

### 接线方式：**只取布尔，不取虫种**

配置在 `server/app/config.py`（`PEST_WEIGHTS` / `PEST_GATE_CONF=0.5` /
`PEST_GATE_ENABLED`），实现在 [pest_gate.py](../server/app/services/pest_gate.py)，
挂在 `/api/detect` 的判型之后：

```
第一步  判型
  YOLO(jktk_x)
    ├─ 有结论 ───────────────────────► 用它，**闸门连跑都不跑**
    └─ 没结论（原始标签 raw: / 无检出）
         └─ 闸门  ─── 响 ──► 「虫害（未定种）」，category=pest
                   └─ 沉默 ──► 「疑似病斑」（原有行为）

第二步  定位            ← 走哪条路取决于第一步
  ├─ 判为虫害 ──► 用**闸门自己的检测框**（method = "pest-gate"）
  └─ 否则     ──► HSV 连通域（method = "lesion-cv"[+fastsam]）
```

四条设计要点，每条都对应上面测出来的一个事实：

1. **闸门只在主判型说不出话时跑。** 闸门是一次完整的模型推理（CPU 上百毫秒），
   而现有三张病害图主判型都有结论 —— 所以它们**连闸门都不会被调用**，输出与接
   闸门之前逐字节相同。这是"纯增益、零回归"最直接的保证。
2. **只读 `fired`，虫种名绝不进入业务结论。** 定种不稳（换四种裁剪四个答案），
   所以 `raw_label` / `confidence` 只作诊断字段透出在 `localization.pestGate`，
   写库、展示、算建议一律不读它。
3. **`pest_gate.py` 从头到尾不调用 `detector.resolve_class`。** 这顺带绕开了一个
   坑：`RAW_LABEL_MAP` 是空的，类别解析全靠 `KEYWORD_RULES` 的宽词匹配，
   拿这个权重的真实标签去跑会张冠李戴 ——

   | 标签 | 现有规则会报成 | 事实 |
   |---|---|---|
   | `corn borer` | 二化螟 | 玉米螟 |
   | `peach borer` | 二化螟 | 桃蛀螟 |
   | `yellow rice borer` | 二化螟 | **三化螟**（不同种） |
   | `rice leafhopper` | 稻飞虱 | 叶蝉（不同科） |

   **不产出的字段就不会被写错** —— 这是结构保证，比"把 `RAW_LABEL_MAP` 填对"
   （要靠人不出错）可靠。所以本权重**不需要**填 `RAW_LABEL_MAP`，也**没有**新增
   `disease_classes` 条目。
   > 这一条推翻了本文件早先那句"接线 = 接权重 + 按真实标签填实 RAW_LABEL_MAP +
   > 补 disease_classes 条目"。那个判断是在"要用它的虫种判定"的前提下下的；
   > 既然只取布尔，那些前置工作就都不必要了。

4. **虫害图的定位改用闸门自己的框，不用 HSV 病灶框。** 这是出图肉眼核对后改的：
   那张幼虫照上 HSV 出的 5 个框**全是茎上的坏死/黄化区，没有一个压在虫体上**，
   还有 1 个落在虚焦背景上。闸门的框虽然松（圈住整段受损茎、不贴虫体），但确实
   把虫体圈在里面 —— 对"虫害"这个断言，**框里有虫比框得紧更重要**。
   代价见下面的「已知限制」。

「虫害（未定种）」（`pest_unidentified`）与「疑似病斑」同类，是**哨兵**不是规范类别：
`disease_classes` 是"病种/虫种"字典，而"未定种"恰恰是**没有类别**，所以它落库时
`detection_records.class_code` 写 **NULL**，`name_cn` 照常写中文名、前端照常显示。
`detection_objects.class_code` 无外键，原样保留哨兵字符串供溯源。
`tools/check_consistency.py` 把它与 `SUSPECT_CN` 一并列入白名单。

### 已知限制（答辩主动说明）

**① 这不是物种识别能力。** 系统的上限是"知道图里有虫、圈出有虫的区间"，不是
"知道是二化螟还是三化螟"。

**② 闸门只在主判型说不出话时才有机会介入。** 一张被主权重**误判成某种病害**的
虫照，闸门不会被问到。这是为"零回归"刻意付的代价。

**③ 虫害框是检测框，偏松。** 实测那张幼虫照上它归一化到
`x 0.353→1.000, y 0.328→0.690`（占图 **23.4%**），虫体只在框的左端一小块里。
由此带出两个**不能当实测值看**的数：

- `infectedAreaRatio = 0.2342` 是**框的面积**，不是量出来的受害面积；
- `severityLevel = "critical"` 是由上面那个面积按既有分档推出的，不是独立判据。

`localization.note` 里已把这句话写死（"该框为检测框、偏松，其面积不等于实测受害
面积"）。**若日后要报真实受害面积，正确的做法是拿受害区域再跑一次分割**，
而不是继续用这个框的面积 —— 那正是本项目一路在避免的"数字看着对"。
